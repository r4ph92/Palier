Deux index portent toute la performance. Un index partiel sur spot (aisle_id, state) WHERE state = 'AVAILABLE' sert la requête d'assignation, qui s'exécute pendant qu'une voiture attend devant une barrière. Un index sur session (lot_id, state) WHERE state IN ('ENTRY_CONFIRMED','PARKED_CONFIRMED','PARKED_UNCONFIRMED') sert la recherche par plaque à la sortie.

Machine à états — place

spot.state

Six états. Trois transitions sont déclenchées par le temps, pas par un acteur : ce sont elles qui empêchent l'inventaire de se vider tout seul.

Machine à états — session

session.state

La session et la place évoluent en parallèle mais pas en miroir : la place peut changer d'état sans que la session bouge, et l'inverse est vrai aussi. Les tenir séparées est ce qui rend le cas « mauvaise place » représentable.

Le seul état où place et session divergent volontairement. Quand l'utilisateur corrige son numéro de place, la session passe à PARKED_CONFIRMED avec confirmed_spot_id différent de assigned_spot_id. Côté places, deux lignes changent dans la même transaction : la place réelle passe à OCCUPIED, l'ancienne à OCCUPIED_UNKNOWN. Écrire ces deux mises à jour hors transaction laisserait une place fantôme à la moindre erreur réseau.

Surface API

4 publics · 3 modes d'authentification

Trois populations très différentes appellent l'API : l'app du conducteur (jeton utilisateur), le matériel de terrain (clé d'appareil), le tableau de bord opérateur (session opérateur). Une quatrième famille n'est appelée par personne — ce sont les tâches planifiées.
