# 034 — Niveaux, allées et balises du stationnement

**Contexte.** #65 : Pierre Roy décrit les niveaux et les allées de son parking, dessine chaque allée en rectangle sur le plan de son niveau (D8, décision 018) et lit ce qu'il faut programmer dans les balises : une région par parking (Q40), le major du parking, un minor par allée, la voie de sortie au minor 0.

**Décision.**
- **UUID de la plateforme** : `PLATFORM_BEACON_UUID = 7B8098B8-9525-4406-AB73-4ABD2095EDC3` dans `packages/shared-types/src/beacons.ts`, un v4 tiré pour Palier et non l'UUID d'usine d'un fabricant (l'ancien `DEVELOPMENT_BEACON_UUID` de l'app, `B9407F30-…`, est celui des balises Estimote neuves : une balise jamais programmée aurait passé pour une allée Palier). L'app (`useAisleMonitoring`, panneau de développement) et l'API lisent la même constante ; `developmentBeacon.ts` disparaît. **À signaler** : une balise déjà programmée avec l'ancien UUID doit être reprogrammée.
- **Migration 0035** : `CHECK aisle_beacon_minor_matches_lane` — voie de sortie ⇔ minor 0, toute autre allée de 1 à 65 535. Avec `UNIQUE (lot_id, beacon_minor)`, il reste au plus une voie de sortie par parking, sans index partiel de plus. Avant la contrainte, la migration ajoute « Sortie » (minor 0) au premier niveau, dans l'ordre d'affichage, de tout parking qui a des niveaux et pas de voie de sortie (Parking Test Paliers) ; le seed la crée aussi. Cet ajout n'a pas de `on conflict` : un parking dont le premier niveau a déjà une allée codée « Sortie », ou une allée ordinaire au minor 0, arrête la migration au lieu de rester sans voie de sortie ; on corrige la donnée, puis on relance.
- **Voie de sortie automatique** : le premier niveau ajouté à un parking sans voie de sortie la reçoit dans la même transaction (`insert … on conflict on constraint aisle_lot_id_beacon_minor_unique do nothing`). Elle n'a pas de rectangle, n'est jamais modifiable, et le tableau de bord la nomme par son rôle (« Voie de sortie », « Exit lane »), jamais par son code stocké.
- **Routes** (toutes sous la session du tableau de bord, classées `DASHBOARD_PROTECTED`) : `GET /v1/dashboard/lots/:id/map` → `{ lotId, lotName, platformUuid, beaconMajor, levels: [{ id, code, displayOrder, aisles: [{ id, code, beaconMinor, isExitLane, rectangle }] }] }` ; `POST …/levels` `{ code }` ; `PUT …/levels/order` `{ levelIds, fromLevelIds }` ; `POST …/levels/:levelId/aisles` `{ code, beaconMinor, rectangle }`. Chaque écriture répond la carte entière, telle qu'enregistrée.
- **Ordre des contrôles** : règle partagée du corps (400) → parking de l'opérateur (verrou `for no key update` sur `parking_lot` filtré par l'opérateur, premier énoncé de la transaction ; sinon `LOT_NOT_FOUND` 404) → niveau du parking (`LEVEL_NOT_FOUND` 404) → contraintes (`LEVEL_CODE_TAKEN`, `AISLE_CODE_TAKEN`, `AISLE_MINOR_TAKEN` 409, lues par le nom de la contrainte ). « Sortie » (`EXIT_LANE_CODE`, dans `beacons.ts`), sous sa forme canonique, est réservé à la voie de sortie sur tous les niveaux : la règle partagée de l'allée le refuse d'emblée (`AISLE_CODE_RESERVED` 400, avec les autres refus du corps), au tableau de bord avant l'envoi comme à l'API, si bien qu'aucune allée où l'on se gare ne se lit comme la sortie. La limite de niveaux passe avant le code pris, comme dans le SQL. Le parking d'un autre opérateur répond donc 404 même avec un code ou un minor pris. Un id mal formé, de parking ou de niveau, répond le `LOT_NOT_FOUND` du parking. Un verrou non obtenu en 3 s répond `LOT_BUSY` 503 avec `Retry-After: 3`, les deux lus d'une seule constante `LOT_LOCK_WAIT_SECONDS`. Le verrou du parking d'un opérateur est `inOwnedLotLock`, à côté de `inLotLock`.
- **Ordre des niveaux** : un niveau ajouté va à la fin (`max(display_order) + 1`). Réordonner envoie la liste complète des ids dans le nouvel ordre (`levelIds`) et l'ordre que la page montrait (`fromLevelIds`). Le serveur refuse (`LEVEL_ORDER_INVALID` 409) un `fromLevelIds` différent de l'ordre enregistré, et tout nouvel ordre qui ne déplace pas un seul niveau d'une seule place : un onglet resté sur un ordre périmé ne défait donc jamais en silence le déplacement qu'un autre onglet a enregistré. `fromLevelIds` est obligatoire (400 sans lui) : sans l'ordre de départ, deux déplacements enregistrés par un autre onglet laissent un écart d'un pas où un ordre périmé passerait. Sur ce refus, la page relit la carte ; si cette lecture échoue aussi, elle le dit (« le plan n'a pas pu être rechargé »). Un seul `update … from unnest(array[…]::uuid[]) with ordinality`. Cet ordre est aussi celui de l'attribution des places (`spotClaim`) : la page le dit.
- **Règles partagées** (`levelDraft`, `aisleDraft`, `aisleRectangle`) : code de niveau et d'allée de 1 à 10 caractères visibles, lus sous leur forme canonique (`canonicalCodeOf` : NFKC, qui replie aussi les lettres pleine chasse comme « Ｐ1 » sur « P1 », toute suite d'espaces, insécables comprises, en une espace, puis `trim`) avant la règle et l'unicité, si bien qu'un « É » décomposé, une espace insécable ou une lettre pleine chasse ne crée pas un second code ; les homoglyphes d'autres alphabets (cyrillique « Р ») sont reportés à une carte de suivi ; sensibles à la casse (« p1 » et « P1 » coexistent) ; minor entier de 1 à 65 535 ; rectangle de la décision 018, vérifié par la même fonction `isAisleRectangle` à l'écriture et à la lecture (`aisleRectangleOf`). Un rectangle absent est refusé (`AISLE_RECTANGLE_INVALID`) : une allée créée au tableau de bord est toujours dessinée. Au plus 20 niveaux par parking (`LEVEL_LIMIT_REACHED` 409). Le tableau de bord ne lit que des entiers pour le rectangle ; l'API accepte les décimaux de la décision 018.
- **Tableau de bord** : `/lots/:id/map` (« Plan et balises », lien depuis la page du parking). Niveaux dans l'ordre avec « Monter » / « Descendre » (« Up » / « Down »), nommés « Monter P2 » pour les lecteurs d'écran, absents pour un niveau seul, désactivés aux extrémités ; le focus reste sur le niveau déplacé, la nouvelle position est annoncée. Le bouton d'ajout de niveau est plein pour le premier niveau, puis en contour : une seule action pleine par vue ; ajout de niveau ; pour le niveau choisi, ses allées, le formulaire d'allée (code, minor, x, y, largeur, hauteur) et l'aperçu SVG du plan cadré sur ses allées avec une marge de 4 % et un rapport largeur/hauteur borné à 4 (une allée de 10 000 × 40 reste visible), aligné à gauche, l'allée en cours en pointillé avec son code ; chaque côté du rectangle a sa propre erreur courte, et l'aide dit que chaque valeur va de 0 à 10 000 sans promettre que le rectangle tient dans la grille (décision 018) ; « Balises » : UUID, major, minor de chaque allée par niveau.

**Hors portée.** Supprimer un niveau ou une allée, changer le minor ou le rectangle d'une allée existante : un minor changé pendant qu'un conducteur est garé fausserait `wrongAisleWalk` et la présomption. Une carte de suivi est ouverte ; d'ici là, une correction passe par la base.

**Preuve SQL.** Le SQL n'est prouvé que sur la base de la voie (002, 005) ; les énoncés ont des tests sur un exécuteur scripté. Scénario joué le 2026-11-13 sur `palier_l65` avec le vrai dépôt (`PostgresLotMapRepository`), puis nettoyé : base seedée migrée en 0035 → Parking Test Paliers reçoit « Sortie » minor 0 sur P1. Garage Roy : P1 puis P2 (ordres 1, 2), « Sortie » minor 0 sur P1 seulement ; permutation → P2 1, P1 2 ; liste incomplète → `LEVEL_ORDER_INVALID` ; allée A minor 1 avec son rectangle relu tel quel ; minor 1 sur P2 → `AISLE_MINOR_TAKEN` ; code A répété sur P1 → `AISLE_CODE_TAKEN` ; P1 répété → `LEVEL_CODE_TAKEN` ; 21ᵉ niveau → `LEVEL_LIMIT_REACHED` ; allée de Pierre sur un niveau de Parking Démo → `LEVEL_NOT_FOUND`. Sophie Lavoie (Stationnements Lavoie) sur Garage Roy : ajout, permutation et allée → `LOT_NOT_FOUND`, lecture → aucune ligne, rien d'écrit. En SQL brut : minor 0 sans voie de sortie et minor 65 536 → `23514 aisle_beacon_minor_matches_lane` ; seconde voie de sortie → `23505 aisle_lot_id_beacon_minor_unique` ; voie de sortie au minor 3 → `23514`. Parking Démo inchangé.

**Migration 0035 rejouée le 2026-11-13** sur une base neuve `palier_l65_check` (migrée de 0000 à 0035, puis seedée) : Parking Démo et Parking Test Paliers ont chacun une voie de sortie « Sortie », minor 0, sur P1. Dans une transaction annulée, sans la contrainte : voie de sortie de Parking Test Paliers retirée → l'ajout de 0035 la remet sur P1 ; voie retirée et allée A renommée « Sortie » → l'ajout échoue sur `aisle_level_id_code_unique` et la migration s'arrête.
